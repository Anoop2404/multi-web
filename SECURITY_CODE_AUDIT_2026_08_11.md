# multi-web (Sahodaya Platform) — Code Quality & Security Audit

**Date:** 2026-08-11
**Scope:** Full repository — Laravel 13 monolith with multi-tenant (stancl/tenancy), Inertia/Vue frontend, Sanctum mobile API, S3-backed uploads.
**Method:** Static/manual review (no PHP runtime available in the sandbox — see *Limitations*). Findings are evidence-based; each cites file/line.

---

## Executive Summary

This is a large (287 controllers, 214 Eloquent models, a 200KB `routes/web.php`) multi-tenant school-federation platform. The core security posture is **better than average** for a project this size: tenant scoping is consistently enforced with explicit `where('tenant_id', ...)` checks in every controller sampled, mass assignment via `$request->all()` was not found anywhere, dompdf's dangerous `enable_php`/`enable_remote` options are correctly disabled, CORS is configured with `supports_credentials: false` and an explicit origin allowlist, login is rate-limited with a dedicated lockout+audit service, and `.env` is properly gitignored and untracked.

No Critical or High-severity, exploitable vulnerability was confirmed in the code reviewed. The issues found are Low/Medium-severity gaps — an admin-only stored-HTML sink, an unvalidated path field, missing throttles on two auth-adjacent endpoints, and an architectural authorization pattern (ad-hoc middleware checks instead of Policies) that increases the risk of a future missed check even though no missed check was found today.

The repository's own history shows an active internal audit practice (11+ prior audit docs in the repo root going back to June 2026), several of which already fixed real issues (an N+1/report-image leak, a public unauthenticated `TypeError`, a registration-number race condition, a privilege-escalation bug in region-scoped admin). This review did not re-litigate those; it looked for what's still open.

**Coverage caveat:** this review sampled representative code across every requested category (auth, tenancy, file handling, CORS/CSRF/session, PDF generation, mass assignment, raw SQL, logging) rather than reading all 287 controllers line-by-line — see *Limitations* for exactly what was and wasn't read, and what to run locally to close the gap.

## Findings, by Severity

### 1. [Low] Stored HTML injection in certificate template body (admin-to-admin XSS)

- **Severity:** Low **Confidence:** Medium
- **Category:** CWE-79 (Improper Neutralization of Input During Web Page Generation)
- **Location:** `app/Http/Controllers/SahodayaAdmin/CertificateTemplateController.php:120,246` (validation: `'body' => 'nullable|string'`, no HTML restriction) and `resources/views/fest/certificate-print.blade.php:104,143,203`
- **Evidence:** The template `body` field is validated only as a plain string. Rendering does escape each interpolated variable (`$safe = e((string) $value)` at certificate-print.blade.php:100) before substituting it into `$body`, but the resulting `$body` — which is otherwise attacker/admin-controlled free text — is then output through `{!! nl2br($paragraph) !!}` (lines 104/143/203) with no `e()`/`strip_tags()` applied to the surrounding text itself.
- **Impact:** A user holding the `sahodaya_admin` role (or a compromised sahodaya-admin session) can embed `<script>`/`<img onerror>` etc. into a certificate template body. It renders in the browser preview (`CertificateTemplateController::preview`, reachable by any user with that role for the same tenant) and could execute in the session of another sahodaya-admin/staff user who opens the same preview or downloaded certificate page. Because dompdf has `enable_php`/`enable_remote` disabled (see Positive Controls), this does **not** escalate to server-side RCE/SSRF via the PDF path — impact is confined to browser-context XSS between users who already hold a fairly trusted role within the same tenant.
- **Recommended remediation:** Escape the paragraph text before `nl2br`, e.g. `{!! nl2br(e($paragraph)) !!}`, or sanitize `body` on save with a strict allowlist (e.g. `strip_tags($body, '<b><i><strong><em>')`).
- **Suggested test:** Feature test that stores a template with `body` containing `<script>alert(1)</script>`, then asserts the rendered preview HTML contains the escaped entity, not a live `<script>` tag.

### 2. [Low] Client-supplied storage path accepted without ownership validation

- **Severity:** Low **Confidence:** Medium
- **Category:** CWE-639 (IDOR) / CWE-22 (Path traversal, partially mitigated by Flysystem)
- **Location:** `app/Http/Controllers/SahodayaAdmin/CertificateTemplateController.php:255` (`'signatories.*.signature_path' => 'nullable|string'`) and the read at line 363 (`$path = $row['signature_path'] ?? ...`)
- **Evidence:** Every other stored-file field in this controller (`logo_path`, `seal_path`, `background_path`, `template_file_path`) is always server-generated by `$file->store(...)`. `signature_path` is the one exception: it's accepted verbatim from client JSON and passed straight into `TenantStorage::logoUrl()` (`app/Support/TenantStorage.php:525`), which builds a display URL from whatever string it's given — checking only whether the path exists on the `public` disk, with no check that it belongs to the acting tenant or was ever produced by that tenant's own upload.
- **Impact:** A sahodaya-admin could reference another tenant's file path on the shared `public` disk if the exact path is known/guessed (filenames are otherwise randomized by `store()`, which limits practical guessability). Flysystem's local adapter normalizes `..` segments, so classic traversal outside the disk root is unlikely to succeed, but this remains an unvalidated-input sink that departs from the pattern used everywhere else in the same file.
- **Recommended remediation:** Drop `signature_path` from client-writable validation; resolve it server-side the same way the other path fields are (only ever set from a fresh upload or the existing DB value), never from raw request input.
- **Suggested test:** Attempt to `PUT` a template update with `signatories.0.signature_path` set to a path outside the tenant's own `sahodaya/{id}/certificate-templates/signatures` prefix and assert it's rejected or ignored.

### 3. [Low] Password-reset endpoints have no explicit rate limit

- **Severity:** Low **Confidence:** Medium
- **Category:** CWE-307 (Improper Restriction of Excessive Authentication Attempts) / CWE-799
- **Location:** `routes/web.php:1503-1509` (`/portal/forgot-password`, `/reset-password` POST routes) — no `throttle:` middleware, unlike `/login` (line 1511: `throttle:20,1`) or the mobile API login (`routes/api.php:36`: `throttle:20,1`) and school-register (`routes/api.php:41`: `throttle:10,1`).
- **Evidence:** Laravel's `Password` broker does apply its own internal per-email cooldown (default 60s) if `AuthController::sendResetLink`/`resetPassword` use the standard broker, which caps abuse against a single email, but there is no IP-based throttle limiting how many distinct email addresses one client can probe per minute — a gap the rest of the auth surface explicitly closes.
- **Recommended remediation:** Add `->middleware('throttle:10,1')` (or similar) to the forgot-password and reset-password POST routes, consistent with the login/register routes.
- **Suggested test:** Hit `/portal/forgot-password` with >10 distinct emails from one IP within a minute and assert a 429 after the threshold.

### 4. [Informational] Authorization is almost entirely ad-hoc, not policy-based

- **Severity:** Informational **Confidence:** High
- **Category:** Maintainability / CWE-284 (Improper Access Control) — architecture risk, not a confirmed vulnerability
- **Location:** `app/Policies/` contains exactly one file, `FestReportPolicy.php`, whose own docblock states: *"First policy class in this codebase... authorization has historically lived in middleware"* (lines 10-16). Across 214 models and 287 controllers, tenant/role checks are hand-written per-controller (e.g., the repeated `abort_if($x->tenant_id !== $this->school->id, 403)` pattern seen in `DownloadController.php:50`, `CertificateTemplateController.php:65,243,348`, and dozens of similar controllers).
- **Impact:** Every reviewed controller in this sample correctly repeats the tenant-ownership check, which is a good sign, but the pattern is manual and unenforced by the framework — there's no structural guarantee a new controller will remember it. This is exactly the shape of bug the repo's own `region_scoped_admin_plan` memory (privilege-escalation fix shipped 2026-08-06) and `type_error_audit_2026_08_06` describe as having happened before.
- **Recommendation (defense-in-depth, not a fix for a found bug):** Introduce Eloquent Policies (or a shared trait/base-controller helper) for the highest-value models (`Student`, `Payment`, `FestRegistration`, `Tenant`) so ownership checks are enforced once, centrally, and covered by a single policy test suite rather than re-derived in each of 287 controllers.

### 5. [Informational] FCM push tokens logged in plaintext

- **Severity:** Informational **Confidence:** High
- **Category:** CWE-532 (Insertion of Sensitive Information into Log File)
- **Location:** `app/Services/Notifications/FcmPushService.php:30,63,65` — `Log::info(...compact('title','body','token'))`, `Log::warning(...['token' => $token])`, `Log::debug(...['response' => $response, 'token' => $token])`
- **Impact:** Device push tokens are not user credentials, but they are semi-sensitive per-device identifiers; anyone with log access could use a leaked token to send spoofed pushes to that device (until the token is invalidated). Low impact, easy fix.
- **Recommendation:** Log a truncated/hashed token (e.g., `substr($token, 0, 12).'…'`) instead of the full value.

### 6. [Informational] `APP_DEBUG=true` / `LOG_LEVEL=debug` in current `.env` and in `.env.example`

- **Severity:** Informational (Low if this configuration were ever deployed to production) **Confidence:** High
- **Category:** CWE-489 (Active Debug Code) / OWASP A05 Security Misconfiguration
- **Location:** `.env:2` (`APP_DEBUG=true`), `.env.example:4`
- **Evidence:** This is the local development `.env` (`APP_ENV=local`), so `APP_DEBUG=true` here is expected and not itself a live exposure. It's flagged because `APP_DEBUG=true` is also the *default* in `.env.example`, which is what a new deploy would copy from if `APP_ENV`/`APP_DEBUG` aren't explicitly overridden in production.
- **Recommendation:** No code change needed; operationally confirm the production `.env` (not reviewed here — out of scope/not accessible) explicitly sets `APP_ENV=production`, `APP_DEBUG=false`, `LOG_LEVEL=error` or `warning`. Consider adding a boot-time guard (e.g., in a service provider) that refuses to start with `APP_DEBUG=true` when `APP_ENV=production`.

## Positive Security Controls Observed

- **Tenant isolation:** every controller sampled (`DownloadController`, `CertificateTemplateController`, `StudentApiController`, `EnsureSahodayaAdmin`, `EnsureSchoolAdmin`) scopes queries by `tenant_id` and independently re-checks `route('tenantId')` against `$user->tenant_id`, including for region/event-admin sub-scoping (`EnsureSahodayaAdmin.php:33-113`, with a documented fix for a prior hub/region leak — see file's own comment at line 129).
- **Mass assignment:** no instance of `$request->all()` flowing into `::create()`/`::update()`/`->fill()` was found anywhere in `app/`.
- **PDF generation hardening:** `vendor/barryvdh/laravel-dompdf/config/dompdf.php` has `enable_php => false` and `enable_remote => false` (lines 236, 270), which closes the two classic dompdf RCE/SSRF vectors even though ~45 controllers/services render user-influenced data through `Pdf::loadView(...)`.
- **CORS:** `config/cors.php` restricts paths to `api/*` and `sanctum/csrf-cookie`, uses an explicit env-driven origin allowlist (not `*`), and sets `supports_credentials => false`.
- **Auth hardening:** `/login` and mobile `/api/v1/auth/login` are throttled (`throttle:20,1`), backed by a dedicated `LoginLockoutService` with lockout messaging and `PlatformAuditLogger` recording both successful and failed logins (`AuthController.php:66-102`). Session tokens are invalidated and regenerated on logout (`AuthController.php:131-133`).
- **Secrets hygiene:** `.env`, `.env.backup`, `.env.production` are all gitignored (`.gitignore`); `.env` is confirmed *not* tracked in git history (`git ls-files` returns nothing for it).
- **Dependencies:** `npm audit` reports **0 vulnerabilities** in the current lockfile. No use of `laravel-lang/*` packages (relevant given the May 2026 supply-chain compromise of that package family). No known CVE was found via search for the pinned major versions of `laravel/framework` (^13.8), `laravel/sanctum` (^4.3), `spatie/laravel-permission` (^7.4), or `stancl/tenancy` (^3.9) as of this review.
- **Dangerous PHP sinks:** no `eval(`, `unserialize(`, `exec(`, `shell_exec(`, `passthru(`, or `proc_open(` found anywhere in `app/`.

## Testing & Coverage Gaps

- `tests/` contains 126 PHP test files across `Unit/`, `Feature/` (split by admin surface: SahodayaAdmin, SchoolAdmin, Admin, State, Public, Api, Events, Services, Console), and a Playwright `e2e/` suite — reasonable breadth for a project this size, but **could not be executed** in this sandbox (no PHP runtime — see Limitations), so pass/fail status and actual assertion coverage were not verified.
- `app/Policies/` has one file covering fest reporting only; the ad-hoc authorization pattern described in Finding 4 has no dedicated policy-level test suite (individual controller tests may cover it implicitly, but this wasn't verified).
- No CI/CD configuration was found in the repository (no `.github/workflows`, no `.gitlab-ci.yml`) — there is currently no automated gate running tests, static analysis, or dependency audits on push/PR.
- The 55 files using `whereRaw`/`selectRaw`/`orderByRaw`/etc. (see command list below) were identified but not individually line-audited for string-concatenated user input; this review sampled adjacent controllers and found parameterized/bound usage patterns throughout, but a full sweep of all 55 files is recommended before treating raw-SQL usage as fully cleared.

## Dependency Risks

- **Could not run `composer audit`** — no PHP or Composer binary available in this sandbox (consistent with prior session finding, see repo memory `sandbox_no_php_runtime.md`). **Action required:** run `composer audit` and `composer outdated -D` locally/in CI before relying on this section.
- `npm audit --production`: **0 vulnerabilities** (frontend build tooling only — Vite/Vue/Tailwind — not shipped to the browser at runtime beyond the built bundle).

## Limitations

- **No PHP/Composer runtime was available in this sandbox** (confirmed dead end — apt, static binary, and WASM PHP were all tried in a prior session per repo memory). This means: no `composer audit`, no static analysis (PHPStan/Larastan/Psalm), no `php artisan route:list`, and the 126-file PHPUnit suite could not be executed. All findings here are from static/manual source review, not from running the application or its test suite.
- Given 287 controllers and 214 models, this review targeted representative, high-risk areas (tenancy middleware, file upload/serving, PDF rendering, mass assignment, CORS/CSRF/session config, auth/rate-limiting, raw SQL usage, logging) rather than reading every file. No confirmed Critical/High vulnerability turned up in the areas reviewed, but the unreviewed surface (the remaining bulk of the 287 controllers, especially payment/ledger and MCQ-exam-mark-entry flows) was not exhaustively checked and should not be assumed clean.
- Web search was used only to check for known CVEs in pinned major dependency versions, not to inspect this application's own code.
