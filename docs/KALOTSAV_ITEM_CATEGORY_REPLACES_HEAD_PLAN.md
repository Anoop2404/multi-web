# Kalotsav: Replace Event Head with an item-level category — Plan

Scope: **non-sports fest programs only** (Kalotsav and similar — `event_type !== 'sports'`). Sports keeps its current Head = Event structure (each sport is its own child `FestEvent`) — that migration already happened (`2026_08_20_000001_sports_event_unified.php`) and is explicitly out of scope here.
Status: **Partially implemented (25 Jul 2026, two passes).** Pass 1: non-sports item creation now captures `category` directly, event-level policy fallbacks are wired (verification/approval/notifications), and the fee resolver already handled headless items correctly with no changes needed. Pass 2: the admin UI to actually set those event-level fields now exists (`LocksTab.vue` — approval policy, capacity caps, notifications). `fest_item_heads`/`fest_competition_areas` were **not** dropped — both passes are additive/backward-compatible, per this doc set's standing convention of not touching schema/migrations without a live database to verify against. See §5.1 and §5.2 for the full account of what shipped and what's still open (biggest remaining piece: category-wise report rewrite, §7). §5's open questions #1/#2 remain blocked on a live database or product input; #3/#4 were answered by reading the code.

## 1. The ask

Stop requiring a separate "Event Head" entity for Kalotsav-type events. Instead, when a Sahodaya admin creates an item, they assign it a plain category directly — no separate head-creation step, no head-level settings screen.

## 2. What exists today (confirmed by reading the code, not assumed)

`FestItemHead` is a real, actively-growing table (columns added incrementally from 2026-07-05 through 2026-07-29 — i.e. genuinely new, still being extended within the last few weeks relative to today, 25 Jul 2026). For Kalotsav specifically:

- **Head creation is a mandatory, separate step from item creation.** An admin creates a head first (`FestItemHeadController::store()`, capturing its full fee/schedule/policy payload in one form), then separately creates items and assigns `head_id` to each via a different screen (`FestItemConfigPanel.vue` inside the Competition Hub). The item creation form itself (`Items/List.vue`) has no head or category field at all today.
- **Kalotsav heads are freeform, admin-typed names** — not a fixed catalog. (The catalog-seeding mechanism, `FestItemHeadService::ensureCatalogHeads()`, is sports-only and no-ops for Kalotsav.) So today's "head" is already close in spirit to a free-text category — the gap is that it also carries a bundle of settings a plain tag can't.
- `FestEventItem` already has its own `category` field (string, validated against the tenant's `arts_category` taxonomy — music/dance/drama/literary/general, configurable per tenant) — but it's a **separate, non-overlapping vocabulary from `head_id` today**, and it isn't even exposed in the main item-creation form (`Items/List.vue`) — only in the master catalog editor (`Items/Master.vue`).
- **A near-duplicate entity already exists and overlaps in scope:** `FestCompetitionArea` (linked via `FestEventItem.area_id`) has almost the identical field set to `FestItemHead` (reg/competition windows, fee defaults, verification/approval policy, capacity caps, venue) and is *also* populated for non-sports events, sitting in the same fee-resolver fallback chain and eligibility checks as the head. Today a Kalotsav item can have both a `head_id` and an `area_id` pointing at two different settings bundles simultaneously. **Any category migration has to say what happens to this overlap — absorb it, remove it too, or leave it coexisting** (see §5, this is the single biggest open question).

## 3. Decided (24 Jul 2026): no per-group settings entity survives — `FestCompetitionArea` goes too

`FestCompetitionArea` (linked via `FestEventItem.area_id`) duplicates almost this entire field set and already sits on Kalotsav items in the same fee-resolver/eligibility paths as the head — it's already non-sports-only in practice (`FestEventController::eventPageContext()` only builds `competitionAreas` when `event_type !== 'sports'`), so removing it alongside `FestItemHead` doesn't touch sports at all. Decision: **both go. `category` is a plain tag with no settings of its own.** Everything below moves to a single event-wide setting instead of a per-head/per-area one:

| Head/Area-level setting today | Where it's actually used | Resolution |
|---|---|---|
| `reg_start`/`reg_end`, `competition_start`/`competition_end`/`competition_time` | `FestItemWindowResolver` — item overrides these, head/area was the fallback tier when an item has no own dates | Item already has its own columns for these. The fallback tier disappears — an item with no explicit dates falls straight to event-level dates. Any Kalotsav event currently leaning on shared head-level windows for many items needs those items to get explicit dates (or accept the event-wide default) once this ships. |
| `default_item_fee`/`extra_item_fee` | `FestItemFeeResolver::amountForItem()` fallback chain — item override → area default → head default → schedule rates | Collapses to: item override → schedule-level participant-type/age-group/class-group rates → schedule default. The per-category pricing tier goes away; pricing becomes purely item-level-override-or-schedule-level. |
| `verification_policy` (verified students only vs all) | `FestRegistrationEligibilityService::validateStudent()` | Becomes a single **event-level** setting. `FestEvent` already has this column and `requiresVerifiedStudentsOnly()` (confirmed 25 Jul 2026, §5 #3) — the read call-site just needs to switch from `$item->head`/`$item->area` to `$event`. |
| `approval_policy` (auto vs manual) | `FestRegistrationApprovalService`, `FestRegistrationCreateService` | Same — single event-level setting, column + helper already exist on `FestEvent` (§5 #3); call-sites need the same switch. |
| `max_participants`/`max_teams` | `FestParticipationLimitService::validateHeadCapacity()` — hard cap/waitlist trigger across every item sharing a head | Per-group capacity capping goes away entirely. If any Kalotsav event actually relies on this today (worth checking before shipping), there's no replacement in this plan — flagging as a real capability loss, not an oversight. |
| `venue` | Display/logistics | Dropped — no replacement field. If venue-per-item info is still wanted, that's a new, separate small feature (item-level `venue` string), not part of this migration. |
| `schedule_mode` + "apply to items" cascade | One-click cascade of a shared date/time to every item under a head | Dropped — pure admin-workflow convenience tied to the head existing; no cascade target once there's no head. |
| `status` (draft/published/registration_open/ongoing/completed) lifecycle | `effectiveStatus()`, registration-open gating | Dropped — event-level `status` remains the only lifecycle gate; no per-group lifecycle. |
| `notification_settings` (per-head trigger gating + extra recipients) | `FestEventNotifier` | Dropped — falls back to `FestEvent::notificationEnabledFor()`/`extraRecipientUserIds()`, which already exist (§5 #3) and were explicitly anticipated for this (see the comment at `FestEventNotifier.php:51`). ~14 call sites need `$head` swapped for `$event`. |
| `is_team_heading` | Drives whether a head becomes its own ID-card section (`FestIdCardService`) | Replaced by `category` directly — ID cards group by category instead. Clean 1:1 swap. |

This is a real simplification, not a lossless refactor — capacity caps, per-group verification/approval policy, and per-group fee tiers are genuine behavior changes for any Kalotsav event actively using them per-head today. Before shipping, check whether any live/recent Kalotsav event actually varies these per head (vs. every head just using the same settings, in which case losing the per-head variation costs nothing in practice).

## 4. Per-head billing (`usesPerHeadBilling()`) — needs a reconciliation step, not just a code change

`FestSchoolEventFeeService::usesPerHeadBilling()` only engages when an event's fee model resolves to `sports_composite`, and the code's own comments repeatedly describe that path as "legacy/transitional," mostly relevant to sports. Kalotsav typically bills via `item_catalog`, not `sports_composite`, so in the common case removing `FestItemHead` doesn't touch billing at all.

**However**, `fee_model` is admin-configurable per event, not hardcoded per `event_type` — so a Kalotsav event *can* be configured to `sports_composite`, and if it has `FestItemHead` rows, `usesPerHeadBilling()` returns true for it today. Before dropping the table: identify any live non-sports event actually in this state (a `FestSchoolEventFee` row with non-null `head_id` where the parent event isn't sports would find these) and reconcile it onto event-level billing first — don't let the table disappear out from under an event with real per-head fee records and payments already made against them.

Answered by reading the code (25 Jul 2026):

3. **Does `FestEvent` already have equivalent event-level fields?** — **Yes, all of them, already.** `FestEvent`'s fillable/casts (`app/Models/FestEvent.php:14-88`) already carry `verification_policy`, `approval_policy`, `notification_settings`, `max_participants`, `max_teams`, `reg_start`/`reg_end`, `competition_start`/`competition_end`/`competition_time`, `default_item_fee`/`extra_item_fee`, `schedule_mode`, `is_team_heading` — added under the comment "Sports unified event fields (formerly on FestItemHead)" during the sports migration, since each sport's child event needed its own copy of exactly this settings bundle. `FestEvent` also already has the matching helper methods (`requiresManualApproval()`, `requiresVerifiedStudentsOnly()`, `notificationEnabledFor()`, `extraRecipientUserIds()`) with identical semantics to `FestItemHead`'s and `FestCompetitionArea`'s own copies. **No new migration or model columns needed for the settings side of this plan.**

   Two things this doesn't give for free, though:
   - ~~No current Kalotsav read call-site consults the event-level fields yet.~~ **Fixed 25 Jul 2026 — see §8.** `FestRegistrationEligibilityService`, `FestRegistrationApprovalService`, `FestRegistrationCreateService`, and all ~14 call sites in `FestEventNotifier` now fall back to `$event->requiresX()` when the item has no head, additively (existing head-based behavior is untouched when a head does exist).
   - **The admin UI to edit these fields directly on a non-sports event doesn't exist yet.** They're currently only editable through the "eligibility"/`sport_event_fees` tab of the event settings screen, which `FestEventSettingsController::edit()` (lines 41-43) actively steers non-sports events away from (`if ($initialTab === 'eligibility' && $event->event_type !== 'sports') { $initialTab = 'lifecycle'; }`). Exposing (or building a Kalotsav-appropriate version of) that tab for non-sports events is a UI task, not a schema change — **still not done**, tracked in §8.

4. **Category taxonomy** — **`arts_category` is already tenant-customizable, not a fixed list.** `FestTaxonomyMaster::DIMENSIONS` (`app/Models/FestTaxonomyMaster.php:18-29`) includes `arts_category` as one of ten first-class dimensions, each with full CRUD per Sahodaya tenant via `FestTaxonomyMasterController::store()/update()/destroy()` — entries are DB-backed (`fest_taxonomy_masters`, scoped by `tenant_id`+`dimension`), falling back to 8 sensible defaults (music/dance/drama/literary/fine_arts/traditional/technology/general, `config/fest_item_taxonomy.php:45-54`) only until a tenant adds its own. This meaningfully de-risks the "lossy forcing into a fixed taxonomy" concern raised in §7: a Sahodaya migrating off freeform head names can pre-seed `arts_category` with entries matching their existing head names before cutover through an admin screen that already exists — a one-time content/data task per tenant, not a technical blocker. **Recommendation: reuse `arts_category` as the taxonomy for `category` rather than inventing a new dimension** — it's already the dimension `FestEventItem.category` validates against (§2), already tenant-scoped and editable, and already has reasonable defaults for a Sahodaya that hasn't customized it.

## 5.1 What shipped in this pass (25 Jul 2026)

Application-level cutover for non-sports events, additive and backward-compatible — no migration, no data touched, `fest_item_heads`/`fest_competition_areas` tables untouched.

- **Item creation now captures `category` directly.** `resources/js/Pages/Admin/Sahodaya/Events/Items/List.vue` gained a "Category" field (populated from `arts_category`) in both the add and edit item forms, plus a Category column in the non-sports item table. The backend already accepted and validated `category` on both `storeItem()`/`updateItem()` (`FestEventController.php`) — this was purely a frontend gap, confirmed by reading the controller before touching anything.
- **Head creation was already dead for non-sports — confirmed, not built.** Before touching UI, checked every route/component that could create a `FestItemHead`. `ItemHeads.vue`'s own route (`item-heads.index`) unconditionally redirects to the competition hub before the page ever renders (`FestItemHeadController::index()`), and the only live "Add Event Head" button (`FestCompetitionSetupBar.vue`) is gated `v-if="isSports && isRoot"` in `ItemHeadOps.vue` — never shown for a Kalotsav event. The only non-sports head UI left standing is `FestItemConfigPanel.vue`'s "Item head" dropdown, which only *assigns* an item to an **existing** head (options: "Unassigned" + current heads) — it has no create action. So no code change was needed to stop new heads from being created for Kalotsav; that already stopped at some earlier point. `app/Http/Controllers/SahodayaAdmin/FestItemHeadController::store()` still technically accepts a non-sports head-creation POST if something hit it directly, but nothing in the app does — left as-is rather than closing off an API surface that isn't the thing anyone asked to change.
- **Event-level policy fallbacks wired in, additively.** `FestRegistrationEligibilityService::validateStudent()`, `FestRegistrationApprovalService::approveSchoolEvent()`, `FestRegistrationCreateService`, and all ~14 notification-gate call sites in `FestEventNotifier` (via a new private `suppressed()` helper) now check `$event->requiresVerifiedStudentsOnly()`/`requiresManualApproval()`/`notificationEnabledFor()` when the item has no head. Existing head-based behavior is untouched when a head does exist (head takes precedence, matching current semantics) — this only newly activates for items with no head, i.e. Kalotsav items created with the new category field. **This is a real, intentional behavior change**: Kalotsav events with `approval_policy`/`verification_policy` set at the event level, or `notification_settings.disabled_triggers` configured, will now actually enforce/respect those for headless items, where before they silently had no effect (the head-only checks always short-circuited to "no restriction" when `$item->head` was null). Worth a quick look at any live event's event-level settings before this reaches production, in case one was set expecting it to do nothing.
- **Fee resolver needed no changes.** `FestItemFeeResolver::amountForItem()` already guards every head/area fee-fallback tier behind `$item?->head_id`/`$item?->area_id` truthiness and falls through cleanly to schedule-level participant-type/age-group/class-group rates when both are null — exactly the §3 resolution, already true today. Confirmed by reading, not assumed.
- **Reports/navigation degrade gracefully, not yet category-aware.** `FestHeadItemNavigationService` already handles zero-heads events without breaking: all items land in a single flat "Other items" group, `hasItemHeads: false`, and `ReportHeadItemNavigator.vue` already renders that flat instead of showing head tabs/chrome (`flatWhenSingleGroup` prop, pre-existing). **Not done**: making that fallback group by `category` instead of dumping everything into one bucket, and the deeper "category-wise" report rewrite (`headWiseSummary()` and siblings keyed by `category` instead of/alongside `head_id`) flagged in §7. Both were judged too large and too risky to attempt without a live database to verify against — the report analytics queries are keyed by real integer `head_id` throughout, and wiring a category-based drill-down means either parallel query paths or a deeper refactor, not a safe one-file change. This remains the biggest piece of downstream work.
- **Not touched, deliberately**: `fest_item_heads`/`fest_competition_areas` tables and their models — still present, still fully functional for any event that already has head-based items (query paths keep preferring the head when one exists).

## 5.2 Event-level policy settings UI (25 Jul 2026, second pass)

The gap flagged at the end of §5.1 — no screen to actually set the event-level fields the fallback logic reads — is now closed, for every event type (not just Kalotsav; sports events get the same fields with no behavior change since the head-first check still wins there).

- **Where it lives**: `LocksTab.vue` (Settings → "General & Operations" → Locks & gates), chosen because — unlike `RegistrationTab.vue` — it's the one tab already rendered unconditionally for every `event_type` (`Settings.vue` gates `RegistrationTab` behind `v-if="isSports"`; `LocksTab` has no such guard). Confirmed by reading `Settings.vue` before picking a home for this, rather than assuming.
- **Approval policy** (auto/manual) and **capacity caps** (max participants/max teams) — added directly to the existing `settingsForm`/`updateSettings()` round-trip (`PUT .../settings`), since they're plain `FestEvent` columns already fillable and already had a request-validation home there for structurally identical fields (`appeal_fee_amount`, etc.).
- **Notifications** — new dedicated form/section (`eventNotifForm`, `saveEventNotifications()`) and a new `PUT .../notification-settings` endpoint (`FestEventSettingsController::updateNotifications()`), deliberately mirroring `FestItemHeadController::updateNotifications()`'s exact validation/recipient-filtering logic (extra recipients must resolve to real platform users in-tenant, never free-text) rather than inventing a new pattern. Needed a new `FestEvent::NOTIFICATION_TRIGGERS` constant — a deliberate copy of `FestItemHead::NOTIFICATION_TRIGGERS`, not a shared reference, matching how the sports migration already copies rather than joins these fields onto `FestEvent`.
- **Verification policy was deliberately left out of this UI.** Investigating where to put it surfaced a pre-existing, already-fully-built, already-working mechanism: `fee_settings.require_verified_students` (tri-state inherit/required/optional) via `StudentVerificationGate`, editable today in this exact same `LocksTab.vue` as "Student verification for item registration" — for every event type, including Kalotsav, already. This is a *different* mechanism from `FestEvent.verification_policy`/`requiresVerifiedStudentsOnly()` (the one wired as a fallback in §5.1), and the two are not the same setting under different names — `StudentVerificationGate` is checked unconditionally first in `FestRegistrationEligibilityService::validateStudent()`, and `requiresVerifiedStudentsOnly()` is a second, additive, stricter-only gate on top. Building a second "require verification" toggle next to the one that already works would have confused admins with two overlapping controls. Net effect: `FestEvent.verification_policy` stays wired (from §5.1) but has no UI and, in practice, is currently dormant for every event — not a regression, just an honestly-documented dead field pending a real decision on whether it's needed at all given `StudentVerificationGate` already covers the same ground.
- **Notification editing for sports Event Heads was already broken before this pass, discovered along the way**: `FestItemHeadOpsController::index()` only populates `notificationTriggers`/`eligibleNotificationUsers` `if ($event->event_type === 'sports')` — but `FestHeadManagePanel.vue`'s own notification block is gated on those same props being non-empty, so per-head notification editing has apparently been unreachable for a while regardless of event type in practice unless that condition is met on a live sports event. Not fixed here (out of scope — this pass only needed to confirm event-level editing was reachable, not audit the pre-existing per-head UI), but worth a look separately.

## 6. Reuse the sports migration as a template

Sports went through structurally the same move (`FestItemHead` → something else) via `2026_08_20_000001_sports_event_unified.php` plus `MigrateSportsHeadToEvent`, `BackfillSportsHeadFees`, `CheckSportsDuplicateHeads`, `MergeDuplicateSportsHeads` console commands. That's a directly reusable pattern: add the new field(s) alongside the old ones, dual-read for a transition period, backfill/migrate existing data via a console command, then remove the old path once nothing reads it. Worth reading those commands command-by-command before writing the Kalotsav version rather than designing the migration mechanics from scratch.

## 7. What this plan deliberately does not decide

- ~~Whether `category` should use the existing `arts_category` taxonomy as-is...~~ **Resolved 25 Jul 2026 — see §5 #4: yes, reuse `arts_category`, it's already tenant-editable.** What's still not decided: the actual per-tenant *mapping* (which of a Sahodaya's current freeform head names maps to which `arts_category` entry, and whether any new `arts_category` entries need creating first) — that's a one-time content exercise per tenant, not a technical design question, and can't be done without seeing each tenant's real head names (blocked on §5 #1's data check).
- UI redesign specifics for `Items/List.vue` (adding the category field to item creation) and what happens to `ItemHeads.vue`/`FestHeadManagePanel.vue` (retire entirely, or keep for sports-only use since sports has its own head concept via child events — actually sports doesn't use `FestItemHead` for live events anymore either, so these two Vue pages may end up Kalotsav-only relics worth reconsidering regardless of this migration).
- Report changes: `headWiseSummary()`/`headWiseParticipantRows()`/`ReportHeadWise.vue`/`ItemHeadOps.vue`/`headOptions()` and everything else in §2's "Reports" list of the research pass would all need to become "category-wise" instead — not scoped here, but flagged as necessarily downstream of whatever §5 decides, and directly relevant to the `docs/SCHOOL_REPORTS_PERFORMANCE_PLAN.md` Phase 3 work already in flight (that phase batches `headWiseSummary()`'s queries — if Kalotsav heads go away, that method's non-sports branch becomes moot for Kalotsav specifically, though it stays relevant for any lingering per-head-billed edge case from §4, and the method's sports branch is entirely unaffected since sports isn't in scope here).
