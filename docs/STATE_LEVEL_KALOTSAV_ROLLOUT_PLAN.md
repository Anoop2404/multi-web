# State-Level Kalolsavam Rollout Plan

**Date:** 31 Jul 2026
**Status:** Pre-rollout plan — Sahodaya conduct starts next week
**Scope:** How to run the state Kalolsavam (state items + Sahodaya items + school items, cascading down; qualifiers cascading back up) across the 6 tenant-managed Sahodayas plus outside Sahodayas/schools that aren't tenants in this system.

This is not a from-scratch design — most of the mechanism already exists (built for the MCS multi-region rollout and the state qualifier pipeline). This doc maps that existing machinery onto the actual rollout and specifies the one genuinely missing piece: intake for Sahodayas/schools outside the 6 managed tenants.

## 1. What already exists (confirmed by reading the code)

**Three-tier item ownership** — already built via `owner_level` on `fest_event_items` (`state` / `sahodaya` / `school`):
- State items come from `FestStateProgramItem` (central) and are locked at both Sahodaya and school level.
- Sahodaya admins add their own items on top (`FestEventController::storeItem()`, `owner_level=sahodaya`) — visible to schools but not editable by them.
- School admins add their own items on top of both (`SchoolAdmin/FestProgramController`, `owner_level=school`) — schools already see all three buckets split out today.

**UI indication of ownership is inconsistent, confirmed 2026-07-31.** School admin's item screen (`Admin/School/Events/ProgramShow.vue`) already renders three clearly labeled sections driven by `ownerLevelLabels` (State / Sahodaya (cluster) / School) — no gap there. But the **Sahodaya admin's** own Kalolsavam item list (`Admin/Sahodaya/Events/Items/List.vue`) is a flat, unlabeled table for non-sports events — no badge, column, or grouping shows whether a row is a state item, a Sahodaya's own item, or (not applicable at that level) a school's. The only ownership indicator that exists anywhere in that file is a plain "State item" text swap-in for the Edit button, and it's gated `v-if="isSports"` — it never renders for Kalolsavam. A Sahodaya admin looking at their item list today cannot tell which rows came from the state catalog vs. which they added themselves. Fix: add a level badge/column to the non-sports table (same table starting at line 116 of that file) reusing the `owner_level` field and `ownerLevelLabels` prop that's already passed to the page — small, contained change.

**State → Sahodaya → school cascade** — already built via `FestStateProgramService`:
1. State admin creates a `FestStateProgram` (central) with its item catalog (`FestStateProgramItem`), sets `conduct_levels` (state/sahodaya/school) and `qualifier_policy`.
2. `publish()` loops every active Sahodaya tenant and creates a `level_round=state` `FestEvent` inside each one, auto-seeded with the state items (`FestItemSyncService::syncProgramToEvent`).
3. Sahodaya conducts normally from there — including region-wise, since this reuses the same `FestPartitionService` from the region/phase plan. `spawnSchoolRounds()` creates one child event per school.

**Qualifier cascade back to state** — already built:
1. `FestQualificationService::promoteWinners()` / `promoteAllSchoolRounds()` moves school-round winners up into the Sahodaya round (same as any normal Kalolsavam).
2. `FestStateQualifierPayloadBuilder` builds the state submission payload from the Sahodaya-round event — and **already understands partitioned/region-wise conduct**: it reads each event's partition role (`region` vs `finale`) and pulls the correct qualifying positions per role from `qualifier_policy`, so a Sahodaya running Tirur + Manjeri + a combined district finale doesn't need any special handling — the finale's winners are what gets submitted.
3. `enqueue()` writes a row to `fest_state_submission_outbox`; `SubmitStateQualifiersJob` / `php artisan fest:process-state-outbox` delivers it to `StateQualifierIntakeController` (idempotent by hash — safe to retry).
4. State side: `StateQualifierIntake` → `StateQualifierEntry` (status `pending`) → `StateQualifierReviewController` approves → `StateFestWorkspaceController::show()` already reads `status=approved` entries to build the state event roster.

**Bottom line for your 6 managed Sahodayas:** next week's rollout is configuration, not new code — create the state program + item catalog, `publish()`, let each Sahodaya (region-wise or not) run its normal flow, submit qualifiers through the existing outbox.

## 2. The gap: Sahodayas/schools outside the 6 managed tenants

`StateFestWorkspaceController` only ever populates registrations from **approved qualifier entries**, and those only ever arrive via a tenant's own `FestEvent` → outbox → API pipeline. There is no self-service tenant onboarding in this codebase and no direct-to-state registration screen. An outside Sahodaya or an unaffiliated school has literally no way in today.

**Decision (confirmed with you, reaffirmed 2026-07-31 after re-checking):** build a lightweight direct-to-state intake form rather than onboarding each outside entity as a full tenant. Re-asked this explicitly given the state-tenancy complications found in §3 — full tenant onboarding reuses more proven code, which is tempting — but you confirmed the outside count is in the **dozens**, and most are unlikely to actually operate the registration/marks-entry software themselves (they just want to send their state qualifiers). That's decisive: full tenant onboarding (subdomain + DB + admin login + school setup, per Sahodaya, each of whom then needs to actually *use* the platform) doesn't scale to dozens of one-off, low-engagement participants in a week — it optimizes for a use case (long-term self-service Sahodaya) that doesn't match this one (a Sahodaya that shows up once a year to hand over a winners list). `StateQualifierIntakeService::receive()` was already written source-agnostic: it takes a `state_program_id`, a `source_tenant_id` **string** (not a real tenant FK), and an `entries[]` array keyed by `school_id`/`school_name` + `item_code`/`item_name` + `student_name`/`position`/`grade`. Nothing about it requires the source to be a real tenant.

At dozens-of-Sahodayas scale, centralizing all data entry through your own state admin team would mean dozens of Sahodayas' worth of manual typing landing on your side — not viable. §2.1 below resolves this with scoped, code-gated access so the work stays with whoever actually has the numbers (the schools).

### 2.1 What to build

**Revised 2026-07-31** — a single flat roster form (school name retyped on every row) doesn't hold up once you account for what's actually happening underneath: a Sahodaya has member schools, and each school has its own qualified students. Re-typing the school name on every student row, for dozens of Sahodayas each with several schools, is exactly the kind of thing that produces typos, duplicate "school" entries that are really the same school spelled two ways, and a slow, error-prone data-entry slog for whoever's filling it in. The fix is to mirror the same two-hop shape the real platform already uses (school → Sahodaya → State) instead of flattening it into one form — but as a lightweight *form structure*, not new master-data tables:

1. **Sahodaya sets up its school list first** (one-time per program): the outside Sahodaya's coordinator (or your state admin, entering on their behalf) adds their participating schools — just name + optional contact, picked once, referenced by every entry after that instead of retyped.
2. **Entries get added under a school**, not floating free: pick the school (from the list just built), then item (from the state catalog), then student/class/position — the school is now a dropdown, not free text, so no duplicate-school-name problem.
3. **Submit** writes into the exact same `StateQualifierIntake`/`StateQualifierEntry` tables as before — no new database entities needed for "School," this is purely a two-step *input flow* over the existing flat schema, keyed so `school_name` is consistent across every entry for that school.

This still doesn't require modeling a real Student/School registry (these are already-decided final results being handed to you, not a live registration process you're managing) — it just fixes the data-entry ergonomics by structuring the *form*, not by building new tables.

**Decision (2026-07-31): each school enters its own students.** Distributes data entry to whoever actually has the numbers, and it isn't inventing a new pattern — it's the exact same shape the manual already uses for the real process: "Passwords for online registration can be obtained by the Sahodaya heads by the date notified by the Kalotsavam office" (manual, General Rules #4). State issues Sahodayas an access credential; here, Sahodayas issue their schools one. Concrete design:

**Two new lightweight central tables** (UUID, `CentralConnection`, same pattern as `FestStateProgram`/`StateDomain` — no new tenant, no Stancl involvement):
- `external_sahodayas` — `state_program_id` (FK), `name`, `contact_name`, `contact_phone`, `contact_email`, `access_code`, `status`.
- `external_schools` — `external_sahodaya_id` (FK), `name`, `contact_name`, `contact_phone`, `access_code`, `status`.

**Access is a short code, not a full user account** — deliberately not building registration/password-reset for an audience that shows up once a year. A state admin creates the `external_sahodayas` row and generates its `access_code`; the coordinator visits a plain code-entry page, and from there adds their schools, each of which gets its own generated `access_code` the coordinator hands off (phone/WhatsApp/email — same as how Sahodaya heads already get their password "by the date notified," per the manual). A school visits its own code-entry page and adds only its own students.

**Flow:**
1. State admin → creates `external_sahodayas` row, shares its code with the Sahodaya coordinator.
2. Coordinator → code-gated page, adds `external_schools` rows, shares each school's code.
3. School contact → code-gated page, adds their qualified students (item from state catalog, student/class/position) — writes `StateQualifierEntry` rows with `school_id` = the `external_schools.id`, `school_name` from that record, `status='pending'` (or a coordinator-review substatus if you want an explicit gate before it's visible to State).
4. Coordinator → reviews entries across all their schools in one list, hits "Submit to State," which calls `StateQualifierIntakeService::receive()` — same code path the tenant API already uses — with `source_tenant_id="external:<sahodaya-name>"` and `qualifier_type='external_entry'` (new value, so these are visually distinguishable from `regional_winner`/`district_winner` in review).
5. State admin → same existing `StateQualifierReviewController` approval screen, no new review UI needed.

**Not yet built** — this is a real feature (2 tables + migration, 3 simple controllers/pages for the 3 personas, code-gated access instead of full auth). Given this touches new schema and this environment has no live database to verify a migration against, this needs a decision on timing before I write it: build it now, or hold this as the spec for whenever you're ready to implement (possibly with real DB access to verify against).

### 2.2 Open questions to settle before building

- ~~Who enters the data — state admin or each outside Sahodaya?~~ **Resolved by §2.1's design: each school enters its own students**, via the code-gated Sahodaya → school delegation.
- **Fee collection for outside entries** — the managed flow presumably collects registration fees through the Sahodaya tenant. Outside entries bypass that; decide whether state-level intake also needs a payment step or whether it's handled offline (bank transfer/DD) and just recorded.
- **Item catalog mismatch** — outside Sahodayas won't have `item_code`s that match your `FestStateProgramItem` catalog automatically; the form should force selection from the state catalog dropdown (not free text) to keep item matching clean for reporting/scoreboards.
- **Access code security** — a short code is deliberately low-friction, but decide the failure mode: rate-limit guesses, expire codes after the registration window closes, and consider requiring the state admin to manually activate an `external_sahodayas` row (rather than self-signup) so a stranger can't create one and start submitting fake schools.

### 2.3 Path to full tenant status in a future year

If an outside Sahodaya later wants to become a real managed tenant (run their own registration/marks-entry like your current 6), there's no migration to build for that — this year's design and the full-tenant path both write into the same shared central tables, so there's no fork to reconcile. Onboarding is just the existing flow you already use: `TenantController::store()` (`type=sahodaya`) + `SahodayaDatabaseProvisioner` creates their tenant, database, subdomain, and admin login, exactly as your current 6 were set up — no new code. This year's `external_sahodayas`/`external_schools` rows and their `StateQualifierEntry` submissions just stay as historical record (`source_tenant_id="external:<name>"`); nothing needs to move. Capturing `contact_name`/`contact_phone`/`contact_email` on `external_sahodayas` now (already in the §2.1 schema) is what makes a post-season "want your own login next year?" follow-up possible — that's the only forward-looking thing this design needs to get right today.

## 3. Blocking gap: the State tenant/database was never actually provisioned

Confirmed 2026-07-31, in response to "we haven't still created the state level tenant" — this is a bigger, more urgent blocker than anything in §4 below, because nothing downstream of qualifier submission can work at all until it's resolved.

`FestStateProgram`, `FestStateProgramItem`, `FestStateProgramPropagation`, and `StateDomain` all explicitly `use CentralConnection` — these already live in your existing central database today, no new tenant needed for program setup/publishing.

But the actual State-side **operational** tables — `state_qualifier_intakes`, `state_qualifier_entries`, `state_fest_events`, `state_fest_registrations`, `state_fest_participants`, `state_fest_marks` — live in a migration file explicitly commented `"run on State tenant database"` (`database/migrations/state/2026_07_20_000001_state_fest_tables.php`), and that intent was never carried through:
- No `state` connection exists in `config/database.php` (only `central` and the per-tenant dynamic connection).
- `database/migrations/state/` is never loaded by anything — `AppServiceProvider` only calls `loadMigrationsFrom(database_path('migrations/tenant'))`; there's no equivalent for `migrations/state`.
- None of the `App\Models\State\*` models (`StateFestEvent`, `StateQualifierIntake`, `StateQualifierEntry`, `StateFestRegistration`, `StateFestParticipant`) declare a `$connection` or use `CentralConnection` — unlike the sibling `StateRemittance` model, which does. If migrated at all today, these tables would silently land on whatever the default connection is, not an isolated State database.
- `EnsureStateAdmin` middleware only checks Spatie roles (`state_admin`/`state_staff`) — it never calls `tenancy()->initialize()` or switches connection, so there's no tenant-switching plumbing wired to a "state" tenant even at the request level.

**Decision (confirmed 2026-07-31): State runs on its own separate domain**, which rules out the central-connection shortcut — that only makes sense if State admins share the same domain/session as the rest of central. Going this route surfaced a bigger finding worth flagging before any code gets written:

**Today, State does not run through Stancl tenancy at all.** All `StateAdmin` routes (`StateQualifierReviewController`, `StateFestWorkspaceController`, `StateBoardResultsController`, etc.) are registered in `routes/web.php` — the central routes file — not `routes/tenant.php`. `EnsureStateAdmin` middleware only checks Spatie roles; it never calls `tenancy()->initialize()`. The `StateDomain.domain` field that already exists is **not** a routing/tenancy domain — reading `StateQualifierIntakeController`, it's the outbound API base URL Sahodayas submit their qualifier outbox *to*, a completely different concept from "which domain serves the State admin UI." So today, whatever domain State admins currently log into is central, full stop.

**Turning State into a genuine separate-domain tenant is more than a config flag — it conflicts with an assumption Stancl's tenancy package makes.** `stancl/tenancy` (as configured here) expects one shared migration path (`database/migrations/tenant`) for every tenant's database — that's how `database_per_sahodaya`/school-shares-Sahodaya's-DB already works. But State's schema (`state_qualifier_intakes`, `state_fest_events`, etc.) is structurally nothing like a Sahodaya's schema (no students, no schools, no fest_events in the Sahodaya sense) — giving State a real tenant row today would migrate the *Sahodaya* schema onto it by default, not `database/migrations/state`. Making this work correctly needs one of:
- A dedicated `TenantDatabaseManager`/migration-path override specifically for `type='state'` tenants (so State gets `migrations/state` instead of `migrations/tenant` when its database is created), plus a `Domain` row pointing State's real domain at that tenant, plus wiring `EnsureStateAdmin` (or a route-group middleware) to call `tenancy()->initialize()` the way tenant routes already do.
- Or, simpler and still domain-correct: keep State's data on the **central connection** (as originally proposed) but still serve `routes/web.php`'s State routes on their own literal domain via `Route::domain(config('state_domain'))` — central data, separate domain, no Stancl tenant machinery involved at all. This gets you "State has its own domain" without fighting Stancl's one-migration-path-per-tenant assumption, at the cost of State not being a physically isolated database.

**Not implemented yet** — this needs a decision on which of those two shapes you actually want (isolated DB via a custom tenant type, vs. own domain on shared central data) before writing the tenancy/migration wiring, and per this codebase's own standing convention (see `KALOTSAV_ITEM_CATEGORY_REPLACES_HEAD_PLAN.md` §5), schema/tenancy changes like this shouldn't be written blind without a live database to verify the migration actually runs correctly.

## 4. Grounded against the official 2026 State Manual

Cross-checked this plan against the Confederation's `Keralam State Sahodaya Kalotsavam Manual 2026` (approved 8 June 2026). Most of it maps directly onto what's already built; two real gaps need a code fix before Sahodaya conduct starts next week, not just configuration.

**Item catalog — reuse, don't re-key.** The manual's full item list (118 individual items across 4 class categories + 11 open/group items, codes 101–511) already exists almost verbatim as `app/Support/data/cksc_kalolsav_items.php` (140 rows, same item codes, same categories/genders/durations, `class_group` already using the `lp`/`up`/`hs`/`hss`/`open` scheme that matches the manual's Category 1–4 exactly). `StateFestProgramController::storeItem()` only supports adding `FestStateProgramItem` rows one at a time through the admin UI today — there's no "import preset" action for the state program screen. **Before next week:** add a one-time import (a console command or an "Import CKSC catalog" button that maps `cksc_kalolsav_items.php` rows into `FestStateProgramItem::create()`) instead of hand-entering 140 items through the form.

**Qualifier quota bug for standard (non-region) Sahodayas.** The manual is explicit: "First and second position winners in each item and in each category shall be selected... only two participants/teams from a Sahodaya are eligible to register in the State level competition" — top 2, always, with English One Act Play capped at exactly 1 team. Reading `FestStateQualifierPayloadBuilder::positionsForRole()`: for a `finale` partition role it correctly uses `qualifier_policy.district.positions` (default `[1,2]`), but for `standard` (i.e. any Sahodaya that isn't running partitioned regions — likely most of your 6) it falls through to a **hardcoded `[1,2,3]`**, which would submit 3rd-place finishers to State. This needs a one-line fix before any non-partitioned Sahodaya submits qualifiers: standard conduct should use the same `district.positions` (or a dedicated `standard.positions`) default of `[1,2]`, not the hardcoded 3-place list.

**English One Act Play has no per-item override.** `positionsForRole()` applies one uniform position list to every item in the event — there's no per-item cap, even though `FestEventItem`/`FestStateProgramItem` already carry a `qualify_count` field that could supply it. Needs a small addition: when building entries for an item, intersect the role-based positions with `min($positions, $item->qualify_count ?? INF)` so an item explicitly configured with `qualify_count=1` (English One Act Play) doesn't submit a 2nd-place team.

**Everything else checked out as already built, no gap:**
- Student caps ("5 single items, max 3 on-stage, or 5 off-stage-only; 2 group items") — `FestParticipationPolicy` already has `max_onstage_per_student`/`max_offstage_per_student`/`max_group_per_student`/`max_total_per_student` and is settable per `level_round` on the state program (`level_policies` in `StateFestProgramController::validateProgram()`). Just needs the right values entered, not new code.
- Appeal fee (₹3,000, forfeited on rejection / refunded on success) — `FestEvent.appeal_fee_amount` + `PortalFestAppealController` already implement fee capture; just set the amount when the state program's events are created.
- Standbys (2 per group, no fee, no certificate) — already modeled (`standbys` count in the item preset, `participant_role='standby'` already excluded from qualification/promotion logic in `FestQualificationService`).
- "One school = one Sahodaya, only registered Sahodayas may submit to State" (manual, General Rules #1–2) — confirms there's no such thing as a raw unaffiliated school registering directly at State; every participant comes through *some* Sahodaya. This validates §2's recommendation: the outside-entry gap is Sahodaya-level only, not a separate school-level intake form.

**Flagged but not solved here (open items, worth a decision before go-live):**

*Court appeal admission* (manual §24, and the analogous school→Sahodaya case). The manual only documents this at the Sahodaya→State hop, but the same real-world situation happens one level down: a student a school didn't pick as its single item nominee (rule 14) can still show up at the Sahodaya round with a court order. Same shape both times — a participant enters a level without having actually qualified, competes and gets graded/certified normally, but their points must NOT count toward their school's or Sahodaya's cumulative trophy totals. No `court_ordered`-style flag exists in any registration/qualifier model today. Design, not yet built:

- **School → Sahodaya hop** (buildable today, no dependency on §3): add a `court_order` value to `FestRegistration.mode` (a plain string column already, no migration needed for new values) so a Sahodaya admin can manually create a registration directly on the Sahodaya-round event for a student who wasn't the school's nominee — bypassing the normal `one_entry_per_item_per_school` cap and the auto-promotion path, since this student never went through `FestQualificationService::promoteWinners()`.
- **Sahodaya → State hop** (blocked on §3 until the State DB exists): same idea using the field that already exists for exactly this purpose — `StateQualifierEntry.qualifier_type` is a free-form varchar today (`regional_winner`/`district_winner` are just conventions, not an enum), so a state admin adding a manual entry (via §2's outside-entry intake screen, or a small addition to `StateQualifierReviewController`) can tag it `qualifier_type='court_order'`.
- **Excluding from totals, both hops:** wherever school/Sahodaya point rankings are computed, filter out `mode='court_order'` (or `qualifier_type='court_order'`) rows. Confirmed today's Sahodaya-level ranking lives in `FestCrossEventReportService::schoolPointsRanking()` (`RPT-KAL-007`/`022`) — needs a `whereDoesntHave` filter added. The State-level equivalent doesn't exist yet at all (another consequence of §3 — there's no `state_fest_marks`-based ranking report built yet).
- Everything else — grading, certificates, item-level results — is untouched; a court-order participant is a completely normal entry within their own item, just invisible to the school/Sahodaya leaderboard math.

*Winner substitution* (manual §28): if a qualified winner can't attend, the Sahodaya may promote the next position — but `StateQualifierSubmissionController::store()` is a single auto-build-and-send action with no manual edit step before submission. A Sahodaya admin currently has no way to swap in the 3rd-place finisher without re-running marks/positions.

## 6. Public results/point-table pages (confirmed 2026-07-31)

**Good news: this already exists for School and Sahodaya level, fully built.** `FestPortalController` (`app/Http/Controllers/Public/`, routes in `routes/tenant.php` under `tenant.fest.*`) is a genuinely public, no-auth results portal — `web` + tenancy-init + `PreventAccessFromCentralDomains` only — resolved per-tenant by domain. It already covers everything "point table and other data on a public URL" implies: event list, event overview, full results with school/category/item/individual/championship tabs, schedule, per-item results, winner posters, PDF export, a live-polling scoreboard, athletic records, and chest-number/name search with the anonymity rules Kalolsavam expects (`FestPublicVisibilityService` — names hidden pre-results at district/state/Sahodaya level, chest-only references). Nothing to build here for School or Sahodaya.

**State level has no equivalent, but that's not a new gap — it's a direct consequence of §3.** `FestPortalController`'s entire pattern depends on `resolveTenant()`/domain-based tenant routing, which State doesn't have (§3: no Stancl tenancy wired for State at all). Once §3's domain/tenancy question is resolved, the same `tenant.fest.*` pattern is the template to reuse for a State results portal — not a new design.

**Real, separate finding: the points table these pages compute from doesn't match the manual.** The school/Sahodaya rankings on these public pages come from `FestGradePointService::pointsForMark()`, summed into `FestResult.total_points`. That service has one special case, `scoring_preset='mcs_kalotsav'` (`config/fest_mcs_scoring.php`: individual A/B/C = 10/7/5, 8/5/3, 5/3/2), and otherwise falls back to a generic `DEFAULT_POINTS` table (A_plus/A/B/C = 10/7/5, 8/5/3, 5/3/2, 3/2/1) hardcoded in the service — **neither matches the actual manual.** Re-deriving the manual's own table (§4, "CALCULATION OF POINTS" — grade points A/B/C = 5/3/1 plus place points 1st/2nd/3rd = 5/3/1, summed): individual A/B/C = **10/8/6, 8/6/4, 6/4/2**; group items are exactly double throughout (already supported structurally — `FestPointRule`/`FestGradePointService` both have an `is_group` flag). Since the manual mandates the *same* manual, including this table, be followed at Sahodaya level too — not just State — this isn't state-only: any Sahodaya conducting this program with results-publish turned on would compute trophies with the wrong table today. Fix: add a new preset (e.g. `scoring_preset='confed_kalotsav'`) mirroring the `mcs_kalotsav` special case with the corrected numbers, set it on every event created for this program (`FestStateProgramService::createTenantEvent()` and `spawnSchoolRounds()` are the two places events get created for it), so it's on by default rather than something each Sahodaya has to remember to configure.

## 7. What this plan deliberately does not cover

- Payment/fee handling for outside entries (§2.2, open question).
- Promoting an outside Sahodaya to a full managed tenant — covered by §2.3, not a gap, just not needed for this rollout.
- Certificate generation / medal tally at state level — out of scope for "getting registrations in," a separate downstream concern; also blocked on §3 since there's no `state_fest_marks`-backed scoring yet.
